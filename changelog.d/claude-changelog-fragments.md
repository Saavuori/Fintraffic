### Changed
- **Changelog entries move out of `CHANGELOG.md` and into a file per pull request**: at roughly a dozen releases a day, two PRs open at once collided twice over — both edited the same lines at the top of `CHANGELOG.md`, and both had to *predict* the version CI wouldn't mint until after the merge, so whichever merged second got a conflict *and* a stale heading. That is how the v0.6.1–v0.8.0 gap happened, and it happened again on the way in here: two PRs both claimed v0.13.0. A PR now writes `changelog.d/<branch>.md` — no version heading, and no lines shared with any other branch, so there is nothing to conflict over and nothing to guess. On merge, `scripts/changelog-fold.js` resolves each pending entry to the release it actually shipped in, folds it into `CHANGELOG.md` under that heading, and deletes it. Nothing about versioning moves: CI still derives the tag from conventional commits exactly as before.
- **The entry's version is derived, never guessed**: a fragment lands in the merge commit and CI tags that commit, so the earliest tag containing it is its release by construction — which means several entries folding at once each land under their own version rather than being lumped together. An entry no tag contains yet (a `scripts/`-only change, say, which `paths-ignore` keeps from cutting a release) is left pending for whichever release picks it up.
- **The PR check asks for an entry rather than policing a heading**: `Reject [Unreleased] placeholder` was the only thing standing between the changelog and a placeholder version, and it could only ever check the text after the fact. The `changelog` job now requires the PR to add a `changelog.d/*.md`, rejects any that carries a `## [vX.Y.Z]` heading, and runs the fold script's own tests — twelve of them, because the fold rewrites the project's public record on `main` unattended. The `[Unreleased]` grep stays as a guard on the fold's output.
- **Renovate writes an entry instead of predicting a version**: `scripts/changelog-entry.js` no longer reads the top heading off the base branch, adds one to the patch number and splices the result into `CHANGELOG.md`. It writes `changelog.d/<its own branch>.md`, which is both simpler and immune to the sibling-merge problem it was carefully engineered around — the rebase-and-regenerate dance in `renovate.json5` existed largely to keep that prediction fresh.

### Notes
- The fold commits to `main`, which is protected, so it authenticates as the Renovate GitHub App (already installed for the same reason — `GITHUB_TOKEN` is not an admin and its push would be rejected). `changelog.d/**` joins `CHANGELOG.md` in the release workflow's `paths-ignore` so that push can't re-trigger the workflow and mint a second tag, the fold job is serialised behind a `concurrency` group, and it rebases and retries if another merge lands underneath it.
